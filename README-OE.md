# oe-client — Orcs & Elves и Orcs & Elves II на движке Tremulous

Один клиент для обеих BREW-игр (Orcs & Elves, 2006; Orcs & Elves II, 2007) на основе
Tremulous GPP1 (ioquake3). Движок играет роль телефона: окно, OpenGL, клавиши, таймер,
звук, файлы сохранений и пользовательские `.bar`/`.mod`. Вся игра — правила, ИИ, скрипты,
меню и программный рендер экрана телефона — живёт в игровом модуле (QVM или DLL), отдельном
для каждой игры.

Код игр взят из реимплементаций oe-re и oe2-re (GPL-3.0); код Tremulous — GPL-2.0-or-later,
поэтому вместе — GPL-3.0 (`LICENSE-GPL3.txt`). Игровых данных в исходниках нет: `.bar` и `.mod`
пользователь кладёт сам.

## Что где лежит

```
src/
  cgame_common/   общее для обоих игровых модулей: vmMain и системные вызовы (oe_game.c,
                  oe_syscalls.c/.asm), BREW-прослойка (brew_shim.c), чтение таблиц из .mod
                  (moddata.c), мини-libc для QVM (vm_libc.c, vmlibc/), интерфейс oe_public.h
  cgame_oe/       Orcs & Elves: код игры из oe-re + oe_main.c (вход модуля, QA-команды)
  cgame_oe2/      Orcs & Elves II: код игры из oe2-re + oe_main.c
  cgame_oeds/     Orcs & Elves DS: код cgame_oe, переведённый на данные картриджа (ds_local.h, ds_data.c)
  oe/             общее для обеих игр в движке — то, что в портах было одинаковым:
                    oe_host.c   «телефон»: загрузка модуля, таймер апплета (тик, потом таймер
                                взводится заново, как ISHELL_SetTimer), BREW-автоповтор клавиш
                                (1500/100 мс), suspend/resume при сворачивании, QA-хуки
                                (OE_PIPE, OE_KEYS, OE_SHOT, ...), системные вызовы модуля
                    oe_bar.c    чтение .bar (ресурсы gzip и строки)
                    oe_files.c  файлы сохранений с семантикой BREW (папка игры в homepath)
                    oe_pmd.c    CMF → PCM; oe_qcelp.c — декодер QCELP-13k (из FFmpeg, LGPL 2.1+)
                    oe_audio.c  10-канальный микшер, sinc-ресемплер 8 кГц → 48 кГц, SDL2
  client/         окно: экран телефона через OpenGL (cl_scrn.c), консоль, клавиши, бинды, модуль ui (cl_ui.c);
                  3D-вид на GPU и карты Quake 3 (cl_hw.c), карты Orcs & Elves DS (cl_dsmap.c)
  ui/             модуль меню выбора игры (запуск без fs_game): base/ui/main.menu в формате Tremulous
  qcommon/ renderer/ sdl/ sys/   движок Tremulous без сервера, сети, cgame, звука и роликов
  tools/          q3lcc/q3asm с поддержкой C99 и long long (нужно для кода игр)
  null/cl_null.c  клиент для oe-headless (QA без окна)
vs2022/           решение Visual Studio 2022 (x64)
Makefile          Linux: oe-headless, QVM-инструменты, QVM и .so модулей (для QA)
```

Что отличается между играми, лежит в модулях: период таймера (O&E 15 мс, O&E II 40 мс),
размер экрана, поведение звука при сворачивании, world_hash и строка статуса для QA-ботов,
отладочные команды (`god`, `noclip`, `tp X Y`, `oemap N`, `devoemap N`, в O&E ещё `ents`, `raise C V`). Движок узнаёт
это через `OE_GAME_INFO` и консольные команды модуля.

## Сборка в Visual Studio 2022

1. Откройте `vs2022\oe.sln`, конфигурация `Release` (или `Debug`), платформа `x64`.
2. «Сборка → Собрать решение».

Всё собирается в `build\`:

```
build\oe.exe                      клиент
build\SDL2.dll
build\oe\vm\oegame.qvm            Orcs & Elves (проект qvm, build_qvm.cmd)
build\oe\oegamex86_64.dll         тот же модуль как DLL
build\oe2\vm\oegame.qvm           Orcs & Elves II
build\oe2\oegamex86_64.dll
build\base\uix86_64.dll           меню выбора игры (проект ui), build\base\vm\ui.qvm — оно же как QVM
build\base\ui\                    файлы меню (копия base\ui)
build\tools\                      q3lcc, q3rcc, q3cpp, q3asm, lburg
```

## Запуск

Положите свои файлы игр рядом с модулями:

```
build\oe\orcsandelves.bar   build\oe\orcsandelves.mod     (сборка 1049: 2099797 и 198280 байт)
build\oe2\orcsandelves2.bar build\oe2\orcsandelves2.mod   (2130702 и 292116 байт)
```

`oe.exe +set fs_game oe` — Orcs & Elves, `oe.exe +set fs_game oe2` — Orcs & Elves II,
`oe.exe +set fs_game oeds` — Orcs & Elves DS (см. ниже). Если файлов нет или версия не та,
появляется окно с объяснением, куда что положить.

### Меню выбора игры (запуск без `fs_game`)

Без `fs_game` клиент работает в папке `base` и, как Tremulous, загружает модуль интерфейса `ui`:
`base\uix86_64.dll` или `base\vm\ui.qvm` (`vm_ui 0`, по умолчанию, — DLL, если она есть, иначе
QVM; `vm_ui 1`/`2` — всегда QVM). Меню описаны в `base\ui\main.menu` в формате меню Tremulous:
`menuDef` / `itemDef` (`rect`, `text`, `textscale`, `textalign`, `forecolor`, `backcolor`, `style`,
`border`, `background`, `decoration`, `autowrapped`, `cvar`, `cvarTest` с `showCvar` / `hideCvar` /
`enableCvar` / `disableCvar`), сценарии `onOpen` / `onClose` / `onESC` / `action` (`open`, `close`,
`exec "команда"`, `setcvar`, `show`, `hide`, `setfocus`), `#include`, `#define`, `enum`
(`base\ui\menudef.h`) и выражения в скобках. Мышь (системный курсор), стрелки/Tab и Enter, Esc.
В консоли: `ui_menu <имя>` открывает меню, `ui_reload` перечитывает файлы меню.

- `vm_use_idtech3_ui` (только чтение) — 1, пока показаны меню папки `base` (клиент запущен без
  `fs_game`); при запуске игры движок ставит 0, и модуль `ui` больше не используется.
- Перед открытием меню движок ставит `ui_installed_oe` / `ui_installed_oe2` / `ui_installed_oeds`
  (1, если файлы игры на месте), и меню показывает недоступные игры бледными.
- `game <папка>` (в меню — `exec "game oe"`) выгружает меню, переключает `fs_game` и поиск файлов
  на папку игры, выполняет её конфиг и запускает игру. Если игра не стартовала, меню возвращаются,
  а причина лежит в `ui_gameError` и показывается в меню `gameerror`.
- Без модуля `ui` (или без `main.menu`) по-старому появляется окно с вопросом, какую игру запустить.

Исходники модуля — `src\ui` (`ui_public.h` — интерфейс с движком, `ui_parse.c` — разбор файлов
меню, `ui_menu.c` — меню и сценарии); движок — `src\client\cl_ui.c`. Проект `ui` решения собирает
DLL и копирует `base\ui` в `build\base\ui`, QVM собирает `build_qvm.cmd`.

Сохранения и настройки: `%APPDATA%\OrcsAndElves\oe\` (и `...\oe2\`), на Linux `~/.oe-client/`.

Модуль: `vm_oegame 0` (по умолчанию) — DLL, если она есть, иначе QVM; `vm_oegame 2` — всегда QVM.
QVM сейчас работает через интерпретатор: в нём O&E тратит около 12 мс на тик (бюджет 15 мс),
поэтому по умолчанию выбрана DLL. JIT для 64-битных инструкций — следующий шаг.

Клавиши (как в портах, меняются через `bind`): стрелки/WASD — ход и повороты, A/D — шаг вбок,
Enter/Space — действие, Esc/Q — левая софт-клавиша (меню), E — правая, Backspace — CLR,
Tab — карта (#), Z/X — оружие (7/*), C — пропуск хода (9), цифры и цифровой блок — цифры
телефона. `~` или Shift+Esc — консоль, Alt+Enter — полный экран.

Окно: по умолчанию полный экран в разрешении рабочего стола (`r_fullscreen 1`, `r_width 0`,
`r_height 0`); Alt+Enter переключает окно/полный экран, окно можно свободно растягивать.

Экран игры (`oe_screen`, `oe_hd`, применяются при запуске игры):
- `oe_screen ""` (по умолчанию) — альбомная раскладка под окно: игра раскладывает экран примерно
  той же высоты, что у телефона, а ширину берёт по пропорциям окна, и всё это увеличивается в целое
  число раз точно на окно (1920x1080: экран 384x216, увеличение 5; 2560x1440: 364x205, увеличение 7).
  3D-вид становится шире, HUD растягивается по ширине; часть 2D-экранов (карта, меню, фон главного
  меню O&E II) рассчитана на узкий экран телефона и рисуется так, как это делает сама игра;
- `oe_screen phone` — исходный портретный экран телефона (176x220), `oe_screen WxH` — свой
  размер от 128x128 до 640x640;
- `oe_hd 1` (по умолчанию) — HD: 3D-вид (стены, пол, монстры, оружие) рендерится в разрешении окна,
  а пиксельная графика HUD, шрифтов и меню увеличивается целыми блоками. Только для DLL-модуля
  (около 7 мс на тик в 1920x1080); QVM рисует экран игры, а окно его увеличивает. `oe_hd 0` — без HD.

## Настройки в меню Options игр

В Options обеих игр (из главного меню и из игрового) после звука идут настройки клиента:
- **HUD scale** (`oe_hudScale`) — во сколько раз увеличен экран игры: Auto (по высоте экрана
  телефона, как раньше) или x1…x8. Чем меньше, тем мельче HUD и шире экран игры. Игра раскладывает
  экран при запуске, поэтому новое значение помечено «(next)» и действует после перезапуска;
- **Resolution** — разрешение окна из списка режимов монитора, или Desktop (разрешение рабочего стола);
- **Fullscreen** — полный экран / окно;
- **Apply video** — применить разрешение и полный экран сразу (`vid_restart`, игра продолжается);
- **Movement** (`oe_moveMode`) — Turns: пошаговое движение оригинала; Steps: свободное движение,
  ход проходит за каждый шаг в новую клетку (и за удар, предмет и т. п., как раньше); Real time:
  свободное движение, шаги хода не тратят, а ход проходит сам каждые `oe_turnTime` мс (500).

Свободное движение: W/S или стрелки вверх/вниз — вперёд/назад, A/D — вбок, стрелки влево/вправо —
поворот, мышь — обзор (вверх/вниз — только в GPU-рендере), левая кнопка мыши — действие/удар
(как select), остальные клавиши — как раньше. Правила игры остаются клеточными: игрок для игры стоит
в клетке и смотрит в одну из четырёх сторон (ближайшую к взгляду), переход в соседнюю клетку — обычный
шаг игры, поэтому стены, двери, монстры и скрипты клеток работают как в оригинале. Скорость —
`oe_moveSpeed` (192 единицы в секунду, клетка = 64), чувствительность мыши — `oe_freecamSensitivity`.

`cl_screenScale 0` — максимально большой с сохранением пропорций, `1` — только целые кратности
(чёткие пиксели), `2` — растянуть на всё окно; `cl_screenFilter 0/1` — без/со сглаживанием.

## Аппаратный рендер (GPU)

`oe_renderer 1` (по умолчанию) — 3D-вид обеих игр рисует рендерер Quake 3 на видеокарте в разрешении
окна, и с DLL, и с QVM; `oe_renderer 0` — только программный рендер игры (см. `oe_hd` выше).
`oe_hwFilter 0` — пиксельные текстуры, как на телефоне (по умолчанию), `1` — сглаженные.

Как это устроено:
- игра по-прежнему выполняет свой программный рендер (в разрешении экрана игры): он участвует в
  логике (будит монстров, отмечает увиденное на карте, ...), поэтому сохранения и QA-трассы не
  меняются. Попутно `Render_drawLine`/`Render_renderSprite` (`render_hw.c` каждой игры) сообщают
  движку, что нарисовано, в мировых координатах: стены срезами по 64 единицы, спрайты-«коробки»
  88×88 тексселей, билборды, клетки пола и потолка, текстуры из палитр (`OE_TRAP_HW_*`, `oe_public.h`);
- движок (`src/client/cl_hw.c`) строит из этого полигоны и шейдеры (`RE_RegisterShaderText`,
  `RE_UploadImageEx` — новые функции рендерера, загрузка карт и `.shader`-скриптов Quake 3 не
  менялась) и рисует `RE_RenderScene` без мира;
- 2D игры (HUD, меню, оружие) накладывается сверху: прозрачно там, где поверх 3D-вида игра ничего не
  рисовала. В QVM программный проход не рисует пиксели 3D (интерпретатору это не по силам), оставляя
  вид цветом-ключом; DLL рисует его полностью, и полупрозрачное 2D поверх 3D точное.

Пока не перенесено на GPU: режим «обесцветить то, что сзади» и цветные оттенки O&E II (синий,
зелёный, красный, фиолетовый) — в такие моменты на месте эффекта видна программная картинка;
полупрозрачные спрайты сортируются не строго по глубине.

## Моды: ресурсы из .pk3

Клиент ищет файлы в папке игры (`oe\`, `oe2\`) и в её `.pk3` (zip). `fs_usepk3 0` — не использовать
`.pk3` (только папку), `1` — использовать (по умолчанию); можно менять и в консоли на ходу.

- **overrides.txt** (в корне `.pk3` или папки) — строки `имя=путь`: ресурс `.bar` с этим именем
  (имя файла из `.bar`, например `Logos.bmp`, `m_01.bsp`; регистр не важен) или с этим номером
  (`6000=maps/m01.bsp` — у O&E часть ресурсов без имён) берётся из `путь`.
  - Картинки (`.bmp` в `.bar`) для игры сохраняют исходный размер, а показываются из файла на их
    месте в разрешении окна: файл может быть больше (HD) и в любом формате (png, tga, jpg, bmp),
    он растягивается ровно на область оригинала (пропорции лучше сохранять, кратность любая).
    Прозрачно — где альфа < 50 % или цвет пурпурный (#FF00FF), как в игре.
  - Всё остальное (карты, таблицы, звуки) отдаётся игре байтами файла, формат должен быть игровой.
- **WTEXELS.txt, STEXELS.txt, FTEXELS.txt** — строки `WALL172=Textures/WTEXELS/WALL172.png`:
  текстура стены / спрайта / пола с номером из ключа (важны цифры в конце) в 3D-виде на GPU
  рисуется из файла, любого размера. Номер — номер в файле текселей: в O&E II запись в
  `wtexels.bin` / `stexels.bin` / `ftexels.bin`, в O&E — ресурс 7512+N (стены), 9000+N (спрайты),
  7000+N (полы). Спрайтам нужна прозрачность (альфа или пурпурный). Программный рендер игры и её
  правила по-прежнему используют оригинал.
- Строки на `//`, `#`, `;` — комментарии. Файлы перечитываются при запуске игры и при смене `fs_usepk3`.
- Если есть HD-картинки (или включён шрифт Q3), экран игры при GPU-рендере (DLL) рисуется в
  разрешении окна, иначе HD не было бы видно; QVM рисует экран игры в её разрешении, картинки
  уменьшаются до него.

**`oe_export`** (в консоли, при запущенной игре) — выгрузка всего, с чего начинается мод, в
`%APPDATA%\OrcsAndElves\<oe|oe2>\export\`:
- `ui/<имя>.png` — картинки из `.bar` (пурпурный фон — прозрачный), `data/<имя>` — остальные
  ресурсы как есть (карты, таблицы, звуки);
- `overrides.txt` — все они, каждая строка закомментирована: в мод оставляют (раскомментируют) строки
  того, что меняют. У ресурсов с одинаковыми именами (много в O&E) ключ — номер, а файл — `<номер>_<имя>`;
- `Textures/WTEXELS/WALLn.png`, `Textures/STEXELS/SPRITEn.png`, `Textures/FTEXELS/FLATn.png` —
  все стены, спрайты (88×88, с прозрачностью) и полы с готовыми `WTEXELS.txt`, `STEXELS.txt`,
  `FTEXELS.txt`. Текстура, которую игра показывает с разными палитрами, выгружается с первой.

Папка — уже рабочий мод: запакуйте её в zip, переименуйте в `.pk3` и положите в папку игры (с ним
игра выглядит как без него). Дальше замените нужные PNG своими (любого размера) и уберите лишнее.

`oe_useidtech3fonts 1` (действует после перезапуска) — шрифты обеих игр рисуются шрифтом id Tech 3
(`gfx/2d/bigchars`, например из `data-1.1.0.pk3` Tremulous в папке игры), вписанным в сетку
игрового шрифта, в разрешении окна; цвет — основной цвет игрового шрифта (подсветка и перекраска
игры работают), особые глифы игры (руны, значки) остаются её. На QVM (без HD-экрана) мелкий шрифт
получается грубым.

## Карты Quake 3 и карты игры

Карты Quake 3 (`.bsp` с текстурами и шейдерами из путей поиска, например pk3 в папке игры):
- `map <карта>` — загружает `maps/<карта>.bsp`. Если игра идёт (и `oe_renderer 1`), включается
  `oe_playover`, иначе свободная камера;
- `devmap <карта>` — то же, но сразу со свободной камерой (`r_testbsp` — старое имя);
- `oe_playover` — игра идёт как обычно (её пошаговые ходы, HUD, меню, оружие, диалоги — от той
  игры, модуль которой загружен), но 3D-вид показывает карту Quake 3: ходы и повороты игрока с
  момента включения откладываются от точки спавна (`info_player_start`, нет её —
  `info_player_intermission`, затем любой `info_player_*`). Стены и столкновения пока от карты игры;
  `oe_playoverScale` — сколько единиц Quake 3 в единице игры (1 по умолчанию, клетка = 64);
- `oe_idtech3freecam` — свободная камера, как у зрителя в Tremulous до выбора команды: без HUD,
  мышь — обзор (в том числе вверх/вниз), W/A/S/D или стрелки — полёт туда, куда смотришь, и вбок,
  пробел — вверх, C/Ctrl — вниз, Shift — быстрее, Escape — назад (туда, откуда включили).
  Работает и на карте Quake 3 (из `oe_playover` или после `devmap`), и на карте самой игры (O&E и
  O&E II, DLL и QVM): игра тогда рендерит свой вид из камеры и всю карту целиком, без отсечения, и
  это увиденное ни на что в игре не влияет (автокарта, монстры не просыпаются). Игра на это время не
  получает клавиш; прочие бинды (например `screenshot`) работают. `oe_freecamSpeed` — скорость
  (320 единиц в секунду, клетка = 64), `oe_freecamSensitivity` — чувствительность мыши (5, как
  `sensitivity` в Quake 3);
- та же команда ещё раз выключает режим. Загруженная карта остаётся, пока не загружена другая
  (это перезапускает рендерер).

Карты самой игры из `.bar`: `oemap N` — перейти на уровень N так, как это делает отладочное меню
игры (O&E: 1 = m01, можно и номер ресурса 6000...; O&E II: 1...), `devoemap N` — то же без
автосохранения при уходе с уровня и с режимом бога. Работают из начатой игры (не из главного меню) и
возвращают обычный вид игры вместо карты Quake 3.

Проверено на ATCS из Tremulous 1.1.0: положите `data-1.1.0.pk3` и `map-atcs-1.1.0.pk3` в папку игры
(`oe\` или `oe2\`) и выполните `map atcs` — текстуры, небо и туман на месте.

## Orcs & Elves DS (`oeds`)

Третья игра — DS-версия O&E: свои уровни и 3D-графика (`src/client/cl_dsmap.c`, форматы — в
`README-OE-DS-MAPS.md`). Положите дамп своего картриджа под именем `rom.nds` в папку `oeds\`
(рядом с `oe\` и `oe2\`); клиент проверяет код игры (`YOEE` — США, `YOEP` — Европа) и читает файлы
прямо из образа. Файл `data/<путь>` в папке `oeds\` или в pk3 там же заменяет файл картриджа
(`data/maps/map_m01.lz`, `data/shaders.bin`, ...) — для модов.

Игра — модуль `cgame_oeds` (`build\oeds\oegamex86_64.dll`, пока только DLL): код игры BREW
(`cgame_oe`), переведённый на данные DS. Меню, HUD, шрифты и звуки — от BREW, поэтому нужны ещё
`orcsandelves.bar` и `.mod` (из `oeds\`, а нет там — из соседней `oe\`). Из картриджа берутся
карты (`.bsp` DS: свои форматы линий, спрайтов, событий, флагов), сущности (`entities.bin`), тексты
(`strings/English/*.bin`), список из 14 карт (номера 6000…6013: свои Brimstone, Burrows, The Forge;
логово дракона — 6011, меню — 6012). 3D-вид рисует движок по карте и спрайтам модуля
(`OE_TRAP_DS_*`). Уже работает: меню, новая игра, загрузка уровня, ходьба по клеткам, сущности
(имена DS, размер монстров), HUD, двери (3D-модели), добыча с тайлами DS, вступление уровня
(команды сценариев DS, плашки помощи с заголовком, катсцены с камерами DS). Ещё нет: части новых
команд DS (LAUNCHFLAMES, RESPAWNMONSTER, LERPSPRITETOOPENTILE), подсказок DS, эмиттеров частиц, звуков
DS, карты мира DS (пока точки карты BREW). `set oe_dsNoMapStart 1` пропускает стартовые события;
`set oe_dsTrace 1` печатает состояния, клавиши и команды сценариев. Для автоматических проверок
`OEDS_CMDS="тик:команда;тик:команда"` выполняет консольные команды на заданных тиках игры (как
`OEDS_KEYS` для клавиш), без фокуса окна.

Без модуля (или без `.bar`/`.mod` BREW) открывается просмотр карт: `oe_dsStartMap` (`map_m01`) с
камерой на точке старта карты (управление как у `oe_idtech3freecam`, Escape открывает консоль):
- `oe_dsWalk 1` (по умолчанию) — ходьба: на высоте глаз, со столкновениями со стенами карты
  (линии `.bsp`, вдоль стен скользит); `oe_dsWalk 0` — полёт сквозь стены (пробел/C — вверх/вниз);
- `oe_dsmap` — список карт, `oe_dsmap <карта>` — загрузить (`map_m01`, или коротко `m01`, `hub`,
  `lava`, `forge`, `bug`, `menu`, `test`); `oe_dsgoto <x> <y> [угол]` — камера в клетку x, y
  (0..31); `oe_dsmodels` — габариты всех моделей `models.bin`;
- геометрия каждой карты — display list'ы 3D-железа NDS (по одному на лист BSP), которые один раз
  при загрузке превращаются в треугольники с текстурами картриджа и запечённым освещением вершин и
  рисуются рендером Quake 3; `oe_hwFilter` — сглаживание текстур, как у BREW-игр;
- спрайты карты (монстры, предметы, факелы, мебель) рисуются так же, как в игре: у «шейдера» спрайта
  есть программа (модели `textures/models.bin`, квады, сдвиги/повороты/масштаб, прозрачность,
  анимация кадров и покачивание по времени) или он рисуется билбордом; свет — из `.light` карты.
  `oe_dsSprites 0` их скрывает. Пока без прокрутки текстур и цветовых бликов материалов.

## Проверка (QA)

`make` на Linux собирает `build/oe-headless` — тот же движок без окна и звука — и модули.
QA-инструменты oe-re/oe2-re работают с ним без изменений через переменные окружения
`OE_*`/`OE2_*` (OE_PIPE, OE_KEYS, OE_TICKS, OE_SHOT, OE_SEED, ...).

Проверено: голден-трассы обоих портов (O&E: entrance, fight, menus, late — 26 536 тиков;
O&E II: caverns, fight, menus — 16 557 тиков) совпадают тик в тик, включая world_hash,
и для DLL, и для QVM; регрессионные тесты портов (level1, save_load, raise_shadow;
caverns_exit, save_load) проходят. Трассы сравнивались с портами, у которых виртуальные часы
включены с самого старта: в оригинальных портах первые миллисекунды до первого тика идут по
реальным часам, из-за чего «случайное событие карты» иногда сдвигается на один тик.
